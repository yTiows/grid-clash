# Grid Clash — External Setup Guide

Everything in this document is work only you can do: creating accounts, agreeing to terms, passing business verification, and making legal decisions. I cannot do any of it on your behalf — I don't have hands to click "Sign Up," and several steps (Stripe's business verification, a lawyer's review) require you specifically.

What I *can* do: every piece of code that consumes what you set up is already written and typechecked against the exact environment variable names below. Where a step can be scripted, there's a script. Where it can't (account creation, business verification), I've marked it **manual, no way around it** so you don't waste time looking for an API to automate a human-identity step that exists specifically because it can't be automated.

**Total hands-on time:** roughly 60–90 minutes if you have your business details ready, plus Stripe's underwriting review (usually same-day, sometimes 1–2 business days).

---

## Order of operations

Do these in order — later steps depend on earlier ones.

1. Supabase (database + auth) — **~15 min**
2. Stripe (payments, identity, payouts) — **~20 min setup + Stripe's review time**
3. Twilio (phone verification) — **~10 min**
4. Local `.env.local` — **~5 min**
5. Deploy: Vercel (app) + Fly.io (match server) — **~15 min**
6. Wire the webhook to your live URL — **~5 min**
7. Legal — **not a "step," an ongoing requirement — read section 7 before taking real money**

## 1. Supabase — database, auth, RLS

### 1.1 Create the project — manual, no way around it

1. Go to **[supabase.com/dashboard](https://supabase.com/dashboard)** → sign up or log in.
2. Click **New Project**.
3. Pick an organization (or create one), name the project (`grid-clash` or similar), set a strong database password — **save this password somewhere**, you'll need it if you ever connect a raw Postgres client.
4. Pick a region close to your users. This can't be changed later without migrating.
5. Click **Create new project**. Takes 1–2 minutes to provision.

### 1.2 Get your keys

Once the project is ready: **Project Settings → API**.

| You'll see | Goes in `.env.local` as |
|---|---|
| Project URL | `NEXT_PUBLIC_SUPABASE_URL` |
| `anon` `public` key | `NEXT_PUBLIC_SUPABASE_ANON_KEY` |
| `service_role` `secret` key | `SUPABASE_SERVICE_ROLE_KEY` |

The `service_role` key bypasses every RLS policy in the schema. It is read only by `src/lib/supabase/admin.ts` and the standalone match server — **never** put it in a `NEXT_PUBLIC_*` variable, and never let it near a Client Component.

Also note your **project ref** — the string in your project URL between `https://` and `.supabase.co`. You'll use it below.

### 1.3 Push the schema — automated

The repo has 33 migrations, already applied and verified against a real, live Supabase project during development — every self-test function (`assert_settlement_works()`, `assert_tournament_entry_works()`, `assert_tournament_completion_works()`, `assert_satellite_completion_works()`, `assert_bounty_claim_works()`, `assert_loyalty_points_mint_works()`, `assert_loyalty_redemption_works()`, `assert_ledger_vocabulary()`, `assert_function_dependencies()`) was executed for real against seeded test accounts, not just applied and assumed correct. Pushing them is one command:

```bash
npx supabase login              # opens a browser to authenticate the CLI
npx supabase link --project-ref YOUR_PROJECT_REF
npx supabase db push            # applies every file in supabase/migrations/ in order
```

`scripts/setup.sh` runs all three for you interactively — see section 4.

**Manual fallback** (if the CLI ever gives you trouble): open **SQL Editor** in the Supabase dashboard and paste-run each file in `supabase/migrations/` in filename order (`20260724000001_...` first). Tedious with 33 files, but works.

### 1.4 Regenerate types after pushing

The repo ships with `src/lib/types/database.types.ts` generated by introspecting the verified schema directly — accurate today, but it's a stand-in. Once your own project is live:

```bash
npx supabase gen types typescript --linked > src/lib/types/database.types.ts
```

Do this any time you add a migration of your own.

### 1.5 Configure Auth

**Authentication → URL Configuration:**
- **Site URL**: your production URL (e.g. `https://gridclash.com`). Use `http://localhost:3000` for local dev.
- **Redirect URLs**: add `http://localhost:3000/auth/callback` for local dev, and `https://yourdomain.com/auth/callback` for production. This is the callback route at `src/app/auth/callback/route.ts` — don't rename that route without updating this.

**Authentication → Email Templates:** Supabase's default email sending works for development but has low rate limits and mediocre deliverability at real volume. Before real users sign up at any scale, connect a transactional email provider (Resend, Postmark, SendGrid all work) under **Authentication → SMTP Settings**. Not required to launch, but plan for it before you need it.

### 1.6 Grant yourself admin — manual, one SQL statement, deliberately no other way

`users.is_admin` defaults to `false` for every account, including yours, and there is intentionally no signup flag, API route, or UI to change it — see `supabase/migrations/20260726000021_admin_and_exclusion_wiring.sql`. The only way to create the first admin is a manual UPDATE, run once:

1. Sign up for a normal account through the app first (this creates your `public.users` row).
2. In the Supabase dashboard, **SQL Editor**, run:
   ```sql
   update public.users set is_admin = true where email = 'you@example.com';
   ```
3. Sign out and back in. `/admin/tournaments`, `/admin/fraud`, and `/admin/disputes` are now reachable — every admin action re-checks `is_admin()` server-side on every call, so this is the only gate that matters.

Grant additional admins the same way. There's no revoke UI either, by the same design choice — `update ... set is_admin = false` if you need to pull access.

## 2. Stripe — deposits, withdrawals, identity verification

This is the biggest piece. Stripe is doing three separate jobs here: taking deposits (Checkout), paying out withdrawals (Connect Express), and verifying identity before a withdrawal is allowed (Identity). All three share one account and one webhook endpoint.

### 2.1 Create your account — manual, no way around it

1. Go to **[dashboard.stripe.com/register](https://dashboard.stripe.com/register)**.
2. You'll need: business name, business type (LLC/Corp — see section 7 if you haven't formed one yet), business address, and a bank account for payouts *to you* (separate from the Connect payouts your platform sends *to players*).
3. Stripe starts you in **test mode** automatically — you can build and test everything below before submitting for live verification.
4. When ready to accept real money: **Dashboard → Activate your account**. Stripe reviews your business (usually fast, occasionally 1–2 business days for higher-risk categories — real-money gaming platforms sometimes get extra scrutiny, so don't leave this until launch day).

### 2.2 Get your API keys

**Developers → API keys**, toggle **Test mode** on while developing.

| You'll see | Goes in `.env.local` as |
|---|---|
| Publishable key (`pk_test_...`) | `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` |
| Secret key (`sk_test_...`) | `STRIPE_SECRET_KEY` |

When you go live, repeat this with **Test mode off** to get your `pk_live_...` / `sk_live_...` pair, and set those in your production environment (Vercel/Fly) — never in a file that gets committed.

### 2.3 Enable Stripe Identity — manual, one-time toggle

Used for KYC before withdrawal (`src/actions/kyc.ts`).

1. **Settings → Identity** (or search "Identity" in the dashboard search bar).
2. Accept the terms, fill in the business details Stripe asks for.
3. That's it — no separate credential. It authenticates with the same secret key above.

### 2.4 Enable Stripe Connect (Express) — manual, one-time setup

Used for withdrawals — each player gets a Connect Express account that Stripe onboards, verifies, and pays out (`src/actions/withdrawal.ts`).

1. **Connect → Get started** (or **Settings → Connect settings**).
2. Choose **Express** as your account type — the code in `src/actions/withdrawal.ts` creates accounts with `type: "express"` specifically. Standard or Custom accounts need different code.
3. Fill in your **platform profile** (what your platform does — be accurate; this is what Stripe uses for its own risk review).
4. Under **Connect settings → Payout settings**, you can review payout schedule defaults for connected accounts. The defaults are fine to start.

### 2.5 Create the webhook endpoint

Every money-confirming event (deposit succeeded, KYC verified, Connect account ready, withdrawal reversed) arrives via webhook at `src/app/api/webhooks/stripe/route.ts`. That route needs a real signing secret to trust what it receives.

**For local development — automated, no dashboard step needed:**

```bash
stripe listen --forward-to localhost:3000/api/webhooks/stripe
```

Install the CLI first if you don't have it: [docs.stripe.com/stripe-cli#install](https://docs.stripe.com/stripe-cli#install). Leave this running in a terminal while you develop — it prints a `whsec_...` value the first time you run it. Put that in `.env.local` as `STRIPE_WEBHOOK_SECRET`.

**For production — automated via script:**

```bash
./scripts/create-stripe-webhook.sh
```

Prompts for your production URL, creates the endpoint via the Stripe CLI subscribed to exactly the six event types the handler acts on, and prints the signing secret to paste into your production environment variables.

**Manual fallback:** **Developers → Webhooks → Add endpoint**, URL = `https://yourdomain.com/api/webhooks/stripe`, select these events:
- `payment_intent.succeeded`
- `account.updated`
- `identity.verification_session.verified`
- `identity.verification_session.requires_input`
- `identity.verification_session.canceled`
- `transfer.reversed`

Copy the **Signing secret** shown after creation into `STRIPE_WEBHOOK_SECRET`. It's shown once — if you lose it, delete the endpoint and recreate it.

### 2.6 Test it without real money

Stripe's test mode has standing test card numbers that never touch real funds:

| Number | Behavior |
|---|---|
| `4242 4242 4242 4242` | Succeeds |
| `4000 0000 0000 9995` | Declines (insufficient funds) |
| `4000 0000 0000 0341` | Succeeds, then dispute-triggers later |

Any future expiry date, any 3-digit CVC, any postal code. For Identity testing in test mode, Stripe provides a test flow that doesn't require a real ID — follow the on-screen prompts in test mode.

## 3. Twilio — phone verification

Used in `src/actions/phone.ts` to gate paid entry on a verified phone number (part of the fraud-prevention layer built into the schema).

### 3.1 Create your account — manual, no way around it

1. **[twilio.com/try-twilio](https://www.twilio.com/try-twilio)** → sign up.
2. You'll be asked to verify your own phone number first — standard Twilio anti-abuse step, unrelated to your app's verification flow.
3. When prompted to create a project, either pick a template or click through to the default — doesn't matter which for this use case.

### 3.2 Get your credentials

Land on the **Twilio Console** after setup. On the main dashboard:

| You'll see | Goes in `.env.local` as |
|---|---|
| Account SID | `TWILIO_ACCOUNT_SID` |
| Auth Token (click "show") | `TWILIO_AUTH_TOKEN` |

### 3.3 Create a Verify Service

Verify handles the SMS-sending infrastructure for you — you do **not** need to separately buy a phone number for this.

1. In the Console, go to **Explore Products → Verify → Services** (or search "Verify").
2. Click **Create new Service**.
3. Give it a name (shows up in the SMS the user receives, e.g. "Grid Clash").
4. Leave channel defaults as SMS.
5. Copy the **Service SID** (starts with `VA...`) into `.env.local` as `TWILIO_VERIFY_SERVICE_SID`.

### 3.4 Trial mode limitation

New Twilio accounts start in **trial mode**, which can only send SMS to phone numbers you've manually verified in the Console (**Phone Numbers → Verified Caller IDs**). Fine for your own testing; add a payment method and upgrade the account before real users hit this flow, or every signup past your own number will silently fail to receive a code.

## 4. Local environment — automated

```bash
cp .env.example .env.local
```

Fill in every value from sections 1–3 above, then:

```bash
./scripts/setup.sh
```

This script:
- Confirms `.env.local` exists and is filled in
- Logs into and links the Supabase CLI
- Pushes all migrations
- Regenerates `database.types.ts` from your live schema
- Tells you the exact `stripe listen` command for local webhook forwarding

Then, two terminals:

```bash
npm install
npm run dev          # Next.js app — localhost:3000
npm run ws-server     # match server — localhost:3001, separate terminal
```

A third terminal running `stripe listen --forward-to localhost:3000/api/webhooks/stripe` if you're testing deposits/withdrawals locally.

## 5. Deployment

### 5.1 Next.js app → Vercel

**Automated via CLI:**

```bash
npm i -g vercel
vercel login
vercel link
vercel env add NEXT_PUBLIC_SUPABASE_URL production
vercel env add NEXT_PUBLIC_SUPABASE_ANON_KEY production
vercel env add SUPABASE_SERVICE_ROLE_KEY production
vercel env add NEXT_PUBLIC_GAME_API_URL production   # your Fly.io WS URL, see 5.2
vercel env add WS_TICKET_SECRET production            # MUST match the WS server's value exactly
vercel env add STRIPE_SECRET_KEY production
vercel env add STRIPE_WEBHOOK_SECRET production
vercel env add NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY production
vercel env add TWILIO_ACCOUNT_SID production
vercel env add TWILIO_AUTH_TOKEN production
vercel env add TWILIO_VERIFY_SERVICE_SID production
vercel env add CRON_SECRET production                 # see below — required for the scheduled standing recompute
vercel --prod
```

Each `vercel env add` prompts you to paste the value. `vercel link` connects this repo to a Vercel project — creates one on first run if none exists.

**Manual fallback:** [vercel.com/new](https://vercel.com/new), import the repo, and paste each variable into **Project Settings → Environment Variables** before the first deploy.

**Scheduled job:** `vercel.json` already declares a cron entry that hits `/api/cron/recompute-standing` every 30 minutes — this is what computes Skill Index, trust band, and fee tier for every player (until it runs at least once, everyone shows a blank Skill Index and the `standard` fee tier, and the leaderboard is empty). Vercel reads `vercel.json` automatically on deploy and attaches `Authorization: Bearer $CRON_SECRET` to every invocation itself, as long as `CRON_SECRET` is set on the project — generate one with `openssl rand -hex 32`. No manual cron setup needed beyond setting that one env var.

### 5.2 Match server → Fly.io

The WebSocket server (`src/server/entrypoint.ts`) is a long-lived process — it can't run on Vercel's serverless model, which is why it's a separate deployment. `Dockerfile` and `fly.toml` are already in the repo.

```bash
curl -L https://fly.io/install.sh | sh    # installs the flyctl CLI
fly auth login
fly launch --no-deploy                     # reads fly.toml, creates the app, skips first deploy
fly secrets set \
  WS_TICKET_SECRET="same value as Vercel" \
  NEXT_PUBLIC_SUPABASE_URL="..." \
  SUPABASE_SERVICE_ROLE_KEY="..." \
  ALLOWED_ORIGINS="https://yourdomain.com"
fly deploy
```

After deploy, `fly status` shows your app's URL (`https://grid-clash-ws.fly.dev` by default). Set that as `NEXT_PUBLIC_GAME_API_URL` on Vercel, using `wss://` (not `ws://`) since it's served over TLS:

```
NEXT_PUBLIC_GAME_API_URL=wss://grid-clash-ws.fly.dev
```

**`WS_TICKET_SECRET` must be byte-identical between Vercel and Fly.** It's an HMAC key — if the two sides disagree, every connection ticket fails signature verification and no one can queue for a match. Generate one value with `openssl rand -hex 32` and use it in both places.

### 5.3 Custom domain

**Manual, standard DNS work:**
1. Vercel: **Project Settings → Domains** → add your domain → Vercel shows you the DNS records to create.
2. At your registrar (wherever you bought the domain), add those records — usually a CNAME or A record. Propagation takes minutes to a few hours.
3. Once your domain is live, go back to Supabase (**Authentication → URL Configuration**) and Stripe (webhook endpoint URL) and update them from `localhost`/the Vercel preview URL to your real domain.

## 6. Post-deploy checklist

Run through this once everything above is live:

- [ ] Sign up for a real account on your deployed URL — confirm the email arrives and the callback redirects correctly
- [ ] Deposit $5 with a Stripe test card, confirm balance updates (check `payment_intent.succeeded` arrived in **Stripe Dashboard → Webhooks → your endpoint → recent deliveries**)
- [ ] Verify your own phone number through the real flow
- [ ] Complete Stripe Identity in test mode
- [ ] Connect a test payout account, confirm `stripe_connect_payouts_enabled` flips true
- [ ] Request a $10 withdrawal, confirm it appears in `payouts` with status `in_transit`
- [ ] Queue for a ranked match from two browser sessions (or two accounts), confirm the WS server pairs them and a match completes
- [ ] Grant yourself admin (§1.6), then confirm `/admin/tournaments`, `/admin/fraud`, and `/admin/disputes` all load
- [ ] Manually trigger `/api/cron/recompute-standing` once (`curl -X POST -H "Authorization: Bearer $CRON_SECRET" https://yourdomain.com/api/cron/recompute-standing`) and confirm it returns `{"recomputed": N}` with `N` equal to your active user count, then check `/leaderboard` shows real rows
- [ ] Confirm the Vercel Cron entry itself fired at least once — **Vercel Dashboard → your project → Cron Jobs** shows recent invocations
- [ ] Flip Stripe to live mode only after all of the above pass in test mode

## 7. Legal and business — not automatable, and not optional

I've built this platform's *technical* compliance surface — self-exclusion that can't be reversed, deposit and loss limits, an age gate at signup, phone and identity verification before withdrawal, a jurisdiction table gating paid entry by state. None of that substitutes for actual legal review, and I want to be direct about exactly where the line is.

**Before you take a single real dollar:**

1. **Business entity.** Stripe's underwriting essentially requires a registered business (LLC or corporation), not a sole proprietorship, for a platform that moves money on others' behalf. If you don't have one, this is step zero — everything in section 2 waits on it.

2. **A lawyer, specifically on skill-gaming/sweepstakes law.** The `jurisdiction_rules` table (`supabase/migrations/.../responsible_gaming.sql`) is seeded with placeholder state restrictions I flagged as "confirm with counsel" in the SQL comments themselves — I do not have reliable, current legal knowledge of which states permit real-money skill contests, and getting this wrong is the single largest legal risk in this entire project. This needs a real answer before launch, not my best guess.

3. **Terms of Service and Privacy Policy.** Also not something I should draft as boilerplate for a real-money product — have a lawyer produce these, informed by what the schema actually does (self-exclusion is permanent, deposit limits tighten immediately and loosen only after a cooling-off period, KYC data goes to Stripe Identity not to your own servers).

4. **Money transmitter licensing.** Depending on your state and how funds flow, you may need one. This is exactly the kind of determination that depends on jurisdiction-specific facts I can't verify — ask your lawyer this directly.

5. **Age verification.** The self-attested date-of-birth gate at signup (`users.date_of_birth_self_attested`) is a first line of defense, not a substitute for the identity verification Stripe Identity performs before withdrawal. Confirm this two-tier approach satisfies your counsel before launch.

I can implement whatever your lawyer determines — update `jurisdiction_rules`, adjust age minimums, add licensing-specific gates — but I can't determine it myself, and I'd be doing you a disservice pretending otherwise.
